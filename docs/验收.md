# Fire Loop 验收套件使用说明

本文件说明 `tests/acceptance/run_m1a_acceptance.py` 怎么跑、结果怎么读、隔离怎么做，
以及为什么**用户电脑上真实 agent 常驻时也能安全验收**。

适用范围：M1a 起的所有里程碑。每个里程碑做完，由 QA 跑一遍并把结果报给 Lead。

---

## 1. 它是什么

`run_m1a_acceptance.py` 是**行为验收**，不是单元测试的替代：

- 真起 agent 进程、真跑 CLI 子进程，逐条核对 `docs/fire-loop-方案.md` 第 5 节验收清单；
- 每次运行都在**完全独立**的管道、互斥体、数据目录里跑，和真实常驻 agent 零冲突；
- 人类可读输出 + 机器可读 JSON 双份结果；
- 成功、失败、脚本内部异常，所有路径都会清场（杀测试进程、删临时目录）。

单测（`python -m unittest discover -s tests -v`）验逻辑，本套件验真实进程行为，两边都要跑。

---

## 2. 快速运行

前置：Windows，解释器 `D:\Python\python.exe`（3.15.1），零第三方依赖，不用 pip install。

```powershell
cd D:\ds植入式
$env:PYTHONPATH = "$PWD\src"
python tests\acceptance\run_m1a_acceptance.py
```

本机实测耗时约 2.6s，全程 0 模型调用、不写注册表、不装服务。

可选参数：

| 参数 | 作用 |
|---|---|
| `--json <path>` | 把机器可读结果写到指定路径；不传则写 `%TEMP%\fireloop-acceptance\result-<时间>-pid<pid>.json` |
| `--skip-graceful-exit` | 跳过 Ctrl+Break 优雅退出项并标 SKIP（无控制台环境用；**默认真测**） |

退出码：

- `0`：全部通过（SKIP 不算失败）；
- `1`：有 FAIL 项，或脚本内部错误，或机器可读结果写不出去。

运行完会在终端末尾打印机器可读 JSON 的实际路径。

## 3. 输出怎么读

### 终端输出

每项一行，格式：

```
[PASS] 2. cli ping → pong，退出码 0 —— exit=0 stdout=pong 耗时=0.10s  (0.10s)
[FAIL] 4. ping/task 连续 5 轮不出现偶发 agent_offline —— #3 ping exit=1 stdout=''  (1.20s)
[SKIP] 8a. agent 收到 Ctrl+Break 优雅退出 … —— 按 --skip-graceful-exit 跳过  (0.05s)
```

- `PASS`：这条验收项通过；
- `FAIL`：这条不通过，`——` 后面是失败现场（退出码、stdout/stderr 摘要、耗时等）；
- `SKIP`：这条不适用（目前只可能是优雅退出相关项，见第 6 节）；
- 行尾 `(…s)` 是该项耗时；
- 末尾汇总：`验收结果：20 项，PASS 20 / FAIL 0 / SKIP 0，耗时 2.62s`，并列出所有失败项。

### 机器可读 JSON

结构（`schema = fireloop.acceptance.v1`）：

```json
{
  "schema": "fireloop.acceptance.v1",
  "suite": "M1a 集成验收",
  "started_at": "...", "finished_at": "...", "duration_s": 2.62,
  "python": {"executable": "...", "version": "3.15.1"},
  "isolation": {
    "pipe_name": "\\\\.\\pipe\\fireloop-accept-<pid>-<uuid8>",
    "mutex_name": "Local\\FireLoopAccept-<pid>-<uuid8>",
    "fireloop_home": "<本次临时 HOME，跑完已删除>",
    "default_pipe": "\\\\.\\pipe\\fireloop-implant",
    "default_mutex": "Local\\FireLoopAgent",
    "real_agent_detected": false,
    "default_pipe_before": false, "default_pipe_after": false,
    "default_mutex_before": false, "default_mutex_after": false
  },
  "options": {"skip_graceful_exit": false},
  "summary": {"total": 20, "passed": 20, "failed": 0, "skipped": 0},
  "exit_code": 0,
  "results": [
    {"id": "0", "name": "...", "status": "PASS", "detail": "...", "duration_s": 0.08}
  ]
}
```

- `summary` 就是计数，CI/脚本直接读它；
- `results[].detail` 与终端 `——` 后面的内容一致，失败时看这里定位；
- `isolation` 是隔离自检证据：`default_pipe_before/after` 与 `default_mutex_before/after`
  必须一致，说明这次验收没有碰生产管道/互斥体；
- `real_agent_detected = true` 表示跑验收时机器上已有真实 agent 常驻（这是正常且安全的情况）。

默认结果文件写在 `%TEMP%\fireloop-acceptance\`，**不进仓库**；这是有意保留的输出，
不属于测试残留（每次运行的文件名不同）。若要清掉，直接删该目录即可。

## 4. 隔离原理（为什么和真实常驻 agent 零冲突）

每次运行生成一套独立环境：

| 项 | 生产值（绝不使用） | 本次验收值 |
|---|---|---|
| 命名管道 | `\\.\pipe\fireloop-implant` | `\\.\pipe\fireloop-accept-<pid>-<uuid8>` |
| 单实例互斥体 | `Local\FireLoopAgent` | `Local\FireLoopAccept-<pid>-<uuid8>` |
| 数据目录 | `%LOCALAPPDATA%\FireLoop\` | `%TEMP%\fireloop-accept-home-<pid>-<uuid8>-XXXX\`（`FIRELOOP_HOME` 覆盖） |

具体做法：

1. 测试 agent 用 `python -m fireloop.agent --pipe-name <隔离管道> --mutex-name <隔离互斥体>` 启动。
   `--mutex-name` 是 T3a 加的入口参数，不传时行为与原来完全一致（默认生产互斥体）。
2. 每次 CLI 调用都显式带 `--pipe-name <隔离管道>`，token 从临时 `FIRELOOP_HOME` 读；
   不会连到生产管道，也不会读用户真实 token。
3. 第二实例测试用隔离互斥体名 + 另一个隔离管道名，验证的是单实例机制本身。
4. 套件里所有子进程都登记在册，清场只 `terminate/kill` **自己拉起的 pid**；
   代码里没有任何按镜像名/进程名批量杀进程的逻辑，不会误杀真实 agent。
5. 唯一的“生产目标”操作是**只读探测**：列一下 `\\.\pipe` 目录、`OpenMutexW` 打开再
   `CloseHandle` 检查生产互斥体是否存在。这不会创建、占用或关闭别人的内核对象。

隔离自检（第 13 项）会在验收开始前后各做一次生产管道/互斥体只读探测，前后状态必须一致；
同时从日志里核对测试 agent 实际使用的管道名和互斥体名确实是本次隔离名。任何一项对不上都记 FAIL。

**结论：真实 agent 常驻时，验收照样全绿；套件既连不到它，也不会杀它。**

## 5. 真实 agent 常驻场景怎么验（QA 自测方法）

当前机器上真实 agent 没在跑时，可以手工模拟这个场景（QA 交付前要做一次）。
开两个终端，**终端 A** 当前台常驻 agent，**终端 B** 跑验收：

```powershell
# 终端 A：用生产管道名 + 生产互斥体名起 agent（临时 FIRELOOP_HOME，不污染真实数据目录）
cd D:\ds植入式
$sim = New-Item -ItemType Directory -Path "$env:TEMP\fl-real-agent-sim" -Force
$env:FIRELOOP_HOME = $sim.FullName
$env:PYTHONPATH = "$PWD\src"
python -m fireloop.agent        # 保持前台运行，看到“已启动，管道 \\.\pipe\fireloop-implant”

# 终端 B：生产管道/互斥体此时都被占着，照常跑验收
cd D:\ds植入式
$env:PYTHONPATH = "$PWD\src"
python tests\acceptance\run_m1a_acceptance.py

# 回到终端 A：确认常驻 agent 还在、还能服务，然后 Ctrl+Break 正常停掉
python -m fireloop.cli ping     # 应打印 pong
```

期望结果：验收 `PASS 20 / FAIL 0 / SKIP 0`，JSON 里 `real_agent_detected = true`、
`default_pipe_before = default_pipe_after = true`，且终端 A 的 `ping` 返回 `pong`（说明没被打扰）。
验证完在终端 A 按 Ctrl+Break 停掉 agent，删掉 `$env:TEMP\fl-real-agent-sim` 目录即可。

注意：给模拟 agent 用临时 `FIRELOOP_HOME` 只是为了避免往真实的
`%LOCALAPPDATA%\FireLoop\` 写日志/token；管道名和互斥体名是生产名，
冲突面与真实常驻 agent 完全一致。

## 6. Ctrl+Break 优雅退出项与 `--skip-graceful-exit`

第 8a 项会给测试 agent 的真实进程组投递 `CTRL_BREAK_EVENT`（等价用户按 Ctrl+Break），
要求退出码 0 且打印“已退出”；第 9b 项随后核对日志里有 `agent_stop`。**默认必须真测。**

两种环境限制：

- 运行套件的地方**没有控制台**（例如某些计划任务/服务上下文）时，Windows 拒绝投递
  `CTRL_BREAK`（`GenerateConsoleCtrlEvent` 失败，错误 6）。套件会自动把 8a/9b 标成 SKIP，
  并用强制终止停掉测试 agent，**不会**算成产品缺陷，其他项照常跑；
- 明确知道当前终端不支持时，也可以手工加 `--skip-graceful-exit`，效果同上（8a/9b 标 SKIP）。

只要环境有控制台（普通 PowerShell 终端、IDE 终端都算），就必须让它真跑；
如果 8a FAIL，说明优雅退出回归了，按 FAIL 处理，不能用 SKIP 掩盖。

## 7. 验收项清单（M1a，共 20 项）

| # | 验收项 | 对应方案条款 |
|---|---|---|
| 0 | agent 未运行时 CLI 快速报错、退出码 1（<2s，不挂死） | M1a 验收第 3 条 |
| 1 | 测试 agent 用隔离管道/互斥体启动并打印启动行 | 入口/隔离 |
| 1b | agent 启动后自动生成 token（64 位 hex） | 方案 3 节鉴权 |
| 2 | `cli ping` → `pong`，退出码 0 | M1a 验收第 1 条 |
| 3 | `cli task` 把任务送到 agent 并回显，退出码 0 | M1a 验收第 2 条 |
| 4 | ping/task 连续 5 轮不出现偶发 `agent_offline`（管道空窗回归） | M1a 实测要求 |
| 5 | 同一隔离互斥体的第二个实例被挡，退出码 1 且打印“已经在运行” | M1a 验收第 5 条 |
| 6 | token 错误时 CLI 明确报错，退出码 3 且打印 `bad_token` | 协议 6 节退出码 |
| 6b | 恢复正确 token 后 CLI 恢复可用 | 回归 |
| 7 | 非法 JSON / 超长行直灌管道后 agent 存活且后续 ping 正常 | M1a 验收第 6 条 |
| 7b | 缺字段 / 未知 type / 超长 task 返回协议错误且 agent 不崩 | 协议错误码表 |
| 8a | Ctrl+Break 优雅退出：退出码 0、打印“已退出” | M1a 验收记录 |
| 8b | agent 退出后 CLI 明确报没在运行，退出码 1 且不挂死 | 协议 6 节 |
| 9 | 日志是 JSONL，含 `agent_start` 且 pipe 为本次隔离管道 | 方案 3 节日志 |
| 9b | 日志 JSONL 含 `agent_stop`（优雅退出路径） | 方案 3 节日志 |
| 9c | 日志不含任务原文与 token（只记长度/sha256 前 8 位） | 协议 7 节安全红线 |
| 10 | 无残留测试进程（隔离管道已消失） | AGENTS 测试清场 |
| 11 | 生产代码无模型 / 网络 / 注册表调用 | M1a 验收第 7 条 |
| 12 | 清场：临时数据目录已删除、`%TEMP%` 无新增残留 | AGENTS 测试清场 |
| 13 | 隔离自检：全程未触碰生产管道/互斥体，真实 agent 状态不变 | 本套件隔离要求 |

---

## 8. 清场保证

- 所有子进程登记在 `Context.procs`，`finally` 里统一 `terminate`（必要时 `kill`）；
- 临时 `FIRELOOP_HOME` 在 `finally` 里 `rmtree`，失败会重试 10 次；
- 成功、失败、脚本内部异常三条路径都走同一套 `finally` 清场；
- 第 10/12 项会把“残留进程/残留临时目录”显式记成 FAIL 并列出具体路径；
- 第 12 项对比的是“本次运行前 `%TEMP%` 已有的 `fireloop-accept-*`”与运行后，
  只把本次新留下的东西算残留，不会冤枉历史遗留。

已做过故障注入验证：故意让脚本在“测试 agent 已启动”后抛异常，确认测试 agent 被杀、
临时目录被删、隔离管道消失、退出码 1，JSON 里记为 `internal` FAIL。

## 9. 排障

| 现象 | 可能原因 / 处理 |
|---|---|
| 第 0 项 FAIL 且耗时接近 2s | 隔离管道意外存在，查机器上是否有别的进程乱建 `fireloop-accept-*` 管道 |
| 第 1 项 FAIL（等不到启动行） | 直接单独跑 `python -m fireloop.agent --pipe-name <唯一名>` 看报错；常见是 `src` 没进 `PYTHONPATH` |
| 第 4 项偶发 FAIL | 管道空窗回归，必须查 `pipe_server.py` 的 accept 循环，不能重试掩盖 |
| 第 5 项 FAIL | `--mutex-name` 回归或单实例逻辑回归 |
| 第 8a 项 SKIP | 当前环境没有控制台（错误 6）；换普通终端复跑，别用 SKIP 交差 |
| 第 8a 项 FAIL | 优雅退出回归，查 `agent.py` 控制台处理器 / `PipeServer.stop()` |
| 第 12 项 FAIL | 有测试进程占着临时目录没退出，按 detail 里的路径查 |
| 第 13 项 FAIL | 严重：验收碰了生产管道/互斥体，或测试 agent 没用隔离名，立即停下排查 |
| `--json` 写失败 | 目标路径不可写；套件按失败返回 1，换 `%TEMP%` 下的路径 |

## 10. 后续里程碑怎么扩

1. 新验收项写成一个返回详情字符串的函数，用 `check(ctx, "<id>", "<名称>", fn)` 注册；
   失败用 `require(条件, "现场说明")`，不适用用 `raise _Skip("原因")`，不要裸抛异常。
2. 必须继续用 `ctx.pipe_name` / `ctx.mutex_name` 起的隔离 agent 和 `ctx.run_cli(...)`；
   **禁止**在验收里出现生产管道名、生产互斥体名的启动/连接操作。
3. 涉及真实常驻进程/系统级行为（M1b 的协议注册、右键菜单、开机自启等）时，
   同样要设计成“可隔离、可回滚、测完清场”，并在本文档补验收项和清理步骤。
4. 每个里程碑完成后，本文第 7 节验收项清单、第 11 节记录都要更新。
